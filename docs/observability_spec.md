# Спецификация наблюдаемости и трассируемости экспериментов (проект, 2026-10-18)

Статус: **проект для следующей кампании** (новый `output_root`). Текущую кампанию `minatar-repair-20261007` не меняет: `experiments/` и `configs/` заморожены до её конца (AGENTS.md).

Цель: (1) любой результат воспроизводим и прослеживается до кода, конфигурации, seeds и входных артефактов; (2) по каждой ветке сохраняется достаточно данных, чтобы **после** эксперимента исследовать, как и почему менялись слои, состояние Adam и качество — не перезапуская обучение. Основной фокус остаётся на экспериментах; логирование идёт параллельно и не должно менять их результат.

**Принцип: телеметрия собирается всегда, фоном (решение пользователя 2026-10-22).**
- **Где.** Во всех новых запусках: обучения источников, ветки ремонтов, контрпримеры, лабораторные замеры, пилоты.
- **Не опция.** Сбор встроен в цикл обучения и включён по умолчанию. Выключать его можно только для проверки побитового совпадения «с логированием и без».
- **Как не замедлить обучение.** Метрики считаются в цикле обучения, а пишутся на диск отдельным потоком. Дорогие метрики (effective rank, L4) считаются реже.
- **Единый формат.** Данные всех запусков пишутся в одном формате и попадают в общий индекс запусков. Тогда помимо самих экспериментов можно делать сквозной анализ: как менялись слои, состояние Adam и метрики обучения во всех запусках, и как это связано с исходами ремонтов.

## 2. Что добавить (уровни)

Слои сети (`experiments/rl_core.py:83`): `conv` (1 456 параметров), `fc_hidden` (131 200), `head` (774); всего ≈ 133 тыс., float32.

**L1. Исходы (усилить).** Финальная и промежуточные оценки — ≥ 100 эпизодов вместо 20 (стоит < 1% времени ветки, `docs/next_campaign_proposal.md` п. 2). Добавить точки кривой 1k и 10k (провал и восстановление после head reset).

**L2. Временные ряды по ветке (скаляры, дёшево).** Каждые 1 000 gradient updates, для каждого слоя `l ∈ {conv, fc_hidden, head}` (и injection-голов, если есть):
- ‖θ_l‖; ‖θ_l − θ_l^pre‖ (сдвиг от точки вмешательства); ‖θ_l − θ_l^0‖ (от инициализации, если θ⁰ восстанавливается из seed — иначе сохранить θ⁰ при создании истории);
- ‖g_l‖ (средний за окно), ‖m_l‖, среднее и 1-й перцентиль √v̂_l, доля параметров с √v̂ < 10·ε;
- эффективный шаг ‖Δθ_l‖/‖θ_l‖ за окно (Lyle et al. 2024, NeurIPS);
- для `fc_hidden`: dormant fraction, effective rank признаков (на фиксированном reference-батче, общем для всех веток истории);
- глобально: средний TD-loss (Huber) за окно, mean/max |Q|, |target|, моменты обновления target, ε, средний return последних эпизодов.

Объём: ≈ 40 скаляров × 50 точек × 576 веток ≈ 1.2 млн чисел — единицы МБ.

**L3. Лёгкие снимки (без replay).** Веса + target + Adam (m, v, step) ≈ 2–2.5 МБ на снимок, в точках 0 (сразу после вмешательства), 1k, 5k, 20k, 50k updates каждой ветки. 576 веток × 5 ≈ 6–7 ГБ (свободно ≈ 106 ГБ на 2026-10-18). Позволяет потом считать любые новые метрики без повторного обучения. Плюс сохранять θ⁰ каждой истории (один раз).

*Решение пользователя 2026-10-18: место не ограничение, сохраняем максимально полно.* Полные снимки с replay (100–200 МБ) в 5 точках × 576 веток ≈ 290–580 ГБ при ≈ 106 ГБ свободных — не помещаются. Поэтому: во всех точках сохраняется всё, **кроме replay** (веса, target, Adam, счётчики, RNG-состояния); replay восстанавливается повторным прогоном ветки от source checkpoint с теми же seeds. **Эту детерминированность нужно проверить в пилоте** (повторный прогон → совпадение sha256 весов и replay в контрольной точке); проверенный ранее побитовый resume шёл от savepoint, содержащего replay, — это не то же самое. Если проверка не пройдёт — сохранять replay в конце ветки для подвыборки веток.

**L4. Дорогие диагностики (редко).** Только в точке до вмешательства и на 50k: усреднение по K = 30 батчам (надёжность одиночного `pre_td_huber` ≈ 0.47, `research/debate/b2_diag_noise.json`); интерференция градиентов (per-sample градиенты на 256 переходах, Lyle et al. 2023); мини-probe (несколько шагов на случайных целях, Lyle 2023 Eq. 5). Стоимость измерить в пилоте до включения.

**L5. Окружение и воспроизводимость.** В манифест — `pip freeze`, версии Python/torch/MinAtar, ОС, число потоков, флаги детерминизма; schema-version для каждого jsonl; sha256 каждого L3-снимка.

## 3. Правила, чтобы логирование не исказило эксперимент

1. **Не трогать RNG обучения.** Диагностики берут батчи из отдельного `RandomState` со своим seed (как сейчас `diagnostics(seed=...)`); reference-батчи фиксируются один раз на историю. Тест: ветка с логированием и без — побитово одинаковые веса на 1k шагов.
2. **Без побочных эффектов на оптимизатор:** только `torch.no_grad` / `autograd.grad`, без `.backward()` в общий граф и без шагов Adam.
3. **Накладные расходы ≤ 5% времени ветки** — измерить в пилоте; L4 отключаем, если дороже.
4. **Атомарная запись** (временный файл → rename) и sha256 — как у существующих checkpoint'ов; resume не должен дублировать точки рядов.
5. **Подтверждающие гипотезы — в prereg до просмотра данных.** Широкое логирование служит разведке; при десятках метрик и 12–24 историях случайная «находка» почти гарантирована.

## 4. Достаточно ли этого, чтобы потом всё оценить

| Вопрос | Сейчас | С L1–L5 |
|---|---|---|
| Помогает ли repair (парный эффект по историям) | да, но шумно (20 эпизодов) | да, точнее (≥ 100 эпизодов) |
| Предсказывают ли диагностики до вмешательства, какой repair лучше | частично: один шумный замер, без слоёв | да для заранее выбранных признаков (K = 30, по слоям); мощность всё равно зависит от числа историй (≈ 24 нужно, `docs/next_campaign_proposal.md`) |
| **Почему** repair помог/навредил (механизм) | нет | частично: видна динамика слоёв, шаг Adam, TD-loss, dormant/rank после вмешательства; причинность — только через дополнительные arms (split-Adam, injection, H-eps/H-timing) |
| Проверка новых метрик задним числом | нет (весов после вмешательства нет) | да, по L3-снимкам без переобучения |
| Воспроизведение любой ветки | да (seeds + SHA + source checkpoint) | да + версии окружения |
| Перенос на отложенные игры | закрыто до freeze (Freeway, Seaquest) | без изменений |

**Чего не даст даже полный лог:** причинного вывода без контрольных вмешательств; надёжного ответа при малом числе независимых историй; поведения replay/данных внутри ветки (replay в L3 не сохраняется — при необходимости сохранять лишь индексы сэмплов или replay в точке 0, ≈ 100–200 МБ).
