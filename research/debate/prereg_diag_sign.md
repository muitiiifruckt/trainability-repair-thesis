# План анализа (v2, зафиксирован до анализа исходов): добавляет ли pre-repair диагностика пользу при выборе head/optimizer reset

Статус: v2 от 2026-10-09 + согласованные изменения v3 (§12, ЕЩЁ НЕ проверены dry-run v3; при расхождении §12 имеет приоритет над §1, §3, §5, §6, §7). Написан и проверен на синтетике ДО какого-либо анализа исходов по diagnostics (в `runs/minatar-repair-20261007/outcomes.jsonl` на момент записи 16 строк = 1 история, breakout seed0; по ней никакой анализ этого плана не делался). Автор: A (Proposer); скептик B остановлен, замечания 1–7 координатора (log.md, «[Координатор в роли скептика]») учтены ниже. После первого запуска на реальных данных файл не редактируется; изменения — только в разделе «Отклонения и версии».
Слово «pre-registered» здесь означает лишь «зафиксировано до анализа исходов»; это внутренний план, не внешняя регистрация.

## 0. Связь с `docs/research_program.md` (замечание 5)
Это **уточнение** этапа 7 протокола («добавочная польза diagnostic Ridge против SBS и age/return Ridge», `docs/research_program.md:64-67`, «Selector и воспроизводимый контракт»), а не его замена. `fit_selectors`/`analyze` из протокола остаются основным анализом и не меняются. Различия (фиксируются как отклонения, см. §11):
- протокол: Ridge предсказывает полный вектор эффектов, alpha из `[0.1,1,10,100]` внутренним grouped CV, критерий — advantage выбора над SBS/age-return; здесь: два отдельных target (head, optimizer), фиксированный alpha=1 (при 12 историях внутренний CV нестабилен), первичная метрика — LOHO-прирост точности предсказания эффекта, решение по знаку — вторичная описательная;
- протокол требует `>=5` историй на игру для не-`uncertain` (там же, `primary_gate`); здесь то же (§8);
- протокол запрещает нормировку по heldout returns; здесь масштаб y берётся только по обучающим историям fold'а (§5).

## 1. Единицы и данные
- Единица независимости, split и bootstrap — `trajectory_id`. Строки: (история, nominal_age); оба возраста одной истории всегда в одном fold. Анализируются только **полные истории**: оба возраста, четыре основных действия, повторы 0 и 1 завершены без `failure_reason`; неполные истории исключаются и перечисляются в отчёте. y строки = среднее по повторам 0,1.
- Reserved-игры (freeway, seaquest) не используются; только `source_mode = natural`.
- Анализ запускается на фиксированном срезе `outcomes.jsonl` (SHA256 среза записывается); пересчёт на более позднем срезе — новый запуск по этому же плану, а не замена первого.

## 2. Цели и множественность
Две первичные цели, α=0.025 на цель (Bonferroni, односторонний тест «польза > 0»):
- T-head: y = j_final(head_reset) − j_final(continue);
- T-opt: y = j_final(optimizer_reset) − j_final(continue).
`head_and_optimizer_reset` и interaction — вторичные, описательные, без вердикта.

## 3. Признаки (замечания 1, 6, 7)
Блоки (все измерены до вмешательства, поля `diagnostics.jsonl`/метаданных checkpoint):
- **Базовые признаки B**: `nominal_age`, `recent_return_mean`, `pre_td_huber`.
- **Блок D_head** (диагностики состояния представления): `feature_entropy_rank_centered`, `dormant_fraction_threshold_0_001`.
- **Блок D_opt** (диагностики состояния optimizer): `gradient_m_cosine` и `m_norm / sqrt_v_norm` (отношение; производная от двух полей того же diagnostics-снимка).
Соответствие «диагностика -> repair» (D_opt для T-opt, D_head для T-head) задано здесь до данных; перекрёстные комбинации — эксплоративные.
**Clock-пакет (замечание 7).** Epsilon в checkpoint считается как `1 − (1 − epsilon_final)·min(1, max(0, steps − warmup)/epsilon_decay)` (`experiments/rl_core.py:270-272`; параметры warmup=5000, epsilon_decay=100000, epsilon_final=0.1, replay_capacity=100000 — `configs/research_program.json:9-11` и `runs/minatar-repair-20261007/config.json`, значения совпадают). Для фактических checkpoint (`diagnostics.jsonl`, все 12) `environment_steps` ∈ {50499, 200499}: epsilon = 0.5905 и 0.1 (прогресс >1 при 200499 срезан), `replay_size` ∈ {50499, 100000}, `gradient_updates` ∈ {45500, 195500}. Следовательно `nominal_age`, epsilon, replay_size, environment_steps, gradient_updates, optimizer_age_* — **один двухуровневый признак** (идеально коллинеарны в дизайне 2 возраста); отдельной «защитной проверки epsilon/replay» (в v1 п.7.3) сделать нельзя — она тривиальна и убрана. Вывод: «age» в baseline = пакет {возраст, exploration, заполнение replay, возраст optimizer}; влияние age не отделяется от exploration/replay в этой панели (замечание B п.5 остаётся открытым ограничением, потребует другого дизайна, например разных epsilon при одном возрасте).
**Запрещено как признаки:** `j_immediate`, `j_final`, любые поля outcomes и производные от них (post-repair), `weight_norm`, `q_abs_max`, `target_abs_max` (кодируют игру/возраст; допускаются в общем whitelist патча `research/debate/patch_whitelist.diff` для эксплоративных селекторов `rl_analysis.py`, но не в этом плане), `pre_td_mse` (дубль `pre_td_huber`), `gradient_norm`, `sqrt_v_norm`, `m_norm` по отдельности, `dormant`/`entropy` вне назначенного блока, любые поля вне списка (чёрные списки не используются). Эксплоративные признаки анализируются отдельной таблицей без вердикта и без права менять эту.

## 4. Игра как скрытый признак (замечания 1–2)
Во всех моделях: свободные (не штрафуемые) intercept'ы по игре; признаки z-score **внутри игры по обучающим историям fold'а** (среднее/sd игры считаются только на обучающих историях, применяются к обучающим и тестовой истории той же игры). Перестановки — внутри игры (§6). Причина: `dormant_fraction_threshold_0_001` — почти метка игры (breakout 0.50–0.70, asterix 0.055–0.27 по `diagnostics.jsonl`), `recent_return_mean` тоже.

## 5. Модели и baseline
Ridge (alpha=1.0, фиксирован), предсказывает y. y делится на sd y в той же игре, посчитанную по обучающим историям fold'а (без центрирования: центрирование стёрло бы среднее по игре, нужное решающему правилу; heldout-returns не используются).
Baseline (предсказание только от перечисленных столбцов + intercept игры): `game` (ничего), `age` {nominal_age}, `age_return` {nominal_age, recent_return_mean}, `loss_return` {pre_td_huber, recent_return_mean}, `base_all` {B}. Лучший baseline выбирается по LOHO-ошибке на тех же данных (консервативно, «in hindsight»).
Кандидат L2 (первичный): B + D(target). Вторичный L1: B vs {game, age} — добавляет ли loss/return сверх возраста (отвечает на вопрос о «простом» baseline, вердикт для L1 не используется в главном выводе).

## 6. Статистика, нулевая гипотеза, интервалы
- LOHO по историям; для истории h: SE_h = среднее квадрата ошибки предсказания по её строкам (в масштабированных единицах).
- T = (mean_h SE_h[лучший baseline] − mean_h SE_h[кандидат]) / mean_h SE_h[лучший baseline] (относительный прирост точности).
- Нуль «D не добавляет сверх B при фиксированной игре»: Freedman–Lane — столбцы D заменяются на fitted(D | B, игра) + остатки, переставленные блоками целых историй **внутри игры**, 99 перестановок, p = (k+1)/100.
- Bootstrap 1000 по историям, **стратифицированный по игре**; лучший baseline фиксируется на наблюдённом. Границы: 2.5% и 97.5% квантили T.
- Вторичная описательная метрика: решение «repair iff предсказанный эффект > 0»; utility истории = средний реализованный эффект выбранного правила; разность с лучшим из {baseline-моделей, continue}; bootstrap-интервал без вердикта.

## 7. Вердикты (для каждого target независимо)
- **positive:** история >= 12 и >= 5 на игру (§8) И T > 0 И p < 0.025 И нижняя граница T > 0.
- **negative:** те же условия по n И верхняя граница T < δ_rel = 0.05 И **gate по dry-run (§9):** на фактическом n (и структуре) dry-run показывает долю ложных negative <= 0.20 при сильном сигнале (b_M = 0.8, ≈ 29% дисперсии y) и долю верных negative >= 0.5 при нуле. Смысл negative: «сильный диагностический сигнал (порядка 30% дисперсии эффекта по предположениям dry-run) исключён; слабые и умеренные (≈10%) НЕ исключены». Формулировать именно так.
- **uncertain:** всё остальное.
Практически: до расширения вердикт всегда uncertain (§8); при 12 историях положительный вердикт маловероятен даже при сильном сигнале (§9).

## 8. Достижимость n (замечание 3)
Основная панель screen: 2 игры × 3 source seeds = 6 историй (по 3 на игру) -> по протоколу `primary_gate = uncertain` (<5 историй на игру) и по этому плану вердикт всегда uncertain. n = 12 (6 на игру) достигается только после расширения source seeds 3,4,5 (`configs/research_program.json`, `confirm.additional_seeds`; `docs/research_program.md`, шаг 5). Порог 12 и 5 на игру зафиксирован сейчас по протоколу и не подбирается под фактическое число; если расширение не состоится, вердикт остаётся uncertain.

## 10. Известные ограничения
- 12 историй — это мало; мощность первичного критерия на сильном сигнале низкая (§9). План главным образом предотвращает постфактумный отбор и определяет, что считать положительным/отрицательным.
- Повторы одной истории не независимы; возрасты одной истории не независимы (учтено блоками).
- Эффект repair измерен с шумом оценки возврата (20 эпизодов) и траекторным шумом; это не уменьшается в процедуре.
- Две игры: leave-one-game-out невозможен; вердикт относится к breakout/asterix.
- Age смешан с exploration/replay-заполнением (§3).
- Блоки D выбраны по механистическим соображениям до данных; другие диагностики — эксплоративные.

## 12. Изменения v3 (приняты 2026-10-09 по входам B2 №4–7 и требованиям координатора; текст написан до анализа реальных исходов; dry-run v3 НЕ выполнен)
Чтобы не менять уже проверенную v2 на ходу, изменения собраны здесь; перед первым анализом реальных данных преемник обязан (а) реализовать их в `scripts/debate_prereg_dryrun.py` (v3), (б) показать на синтетике ложные положительные, (в) занести результаты в §9 и в «Отклонения»; если какое-то изменение v3 не проходит dry-run (ложные положительные > номинала), оно откатывается к v2 с записью причины.
1. **j_pre в baseline** (замечание координатора 1, P5): блок B = {`nominal_age`, `recent_return_mean`, `pre_td_huber`, `j_pre`}, где `j_pre` — greedy-оценка до вмешательства (`checkpoints.jsonl`, одинакова у всех arms). Причина (B2, 6a): `recent_return_mean` — ε-greedy тренировочный return; внутри возраста 50k его корреляция с истинным качеством −0.84 (n = 3 breakout-checkpoint), у `j_pre` +1.00.
2. **Двухуровневый вердикт** (P1): «информативно» = T > 0 и p < 0.025 (перестановки, ≥ 9 999); «практически полезно» = информативно И нижняя граница T > 0 (стратифицированный bootstrap). Сообщаются оба уровня; claim о пользе — только второй.
3. **Нулевое распределение устойчивое к связанной гетероскедастичности** (P6): добавить сценарий `null_hetero_coupled` (масштаб истории lognormal, log-sd 0.8, общий для шума D и шума y; по B2 v2-перестановки дают 8.5–10.4% вместо 2.5%). Кандидаты на смягчение: ранговые нормальные scores D и y внутри игры (по обучающим историям fold'а, без heldout), знаковые перестановки блоков остатков (знак на всю историю). Выбор — по доле ложных положительных в dry-run v3 (цель ≤ 2.5–3% при 400+ симуляциях); если ни один вариант не достигает, уровень «информативно» помечается как приблизительный, а решения принимаются только по уровню «полезно».
4. **Компаратор задан заранее** (P2, замечание координатора 4): L2 — `base_all` (блок B из п.1), L1 — `age`. Best-of-5 «в hindsight» показывается как описательная чувствительность и НЕ входит ни в positive, ни в negative (по B2 он завышает долю «UB < истинный T» до 7–17%).
5. **Усреднение по всем завершённым repeat** (P4): y истории = среднее по repeat 0..R*−1, где R* — максимальное число, завершённое для всех анализируемых историй и всех четырёх действий (не только 0 и 1); R* фиксируется в отчёте. Добавить сценарий с 4 repeat (шум в √2 раз меньше).
6. **Reliability gate до диагностического теста** (P8): split-half/ICC(1) эффекта по repeat после вычитания средних game × age; порог ≥ 0.3 (порог и оценка шумны на 24 ячейках — dry-run v3 должен показать долю прохождения при истинном ICC 0, 0.15, 0.3, 0.5). Не пройдён -> вердикт «неидентифицируемо» (не negative). По B2 (вход 7, 40 строк, breakout) ICC эффекта head_reset ≈ −0.27, т.е. для T-head вердикт «неидентифицируемо» вероятен; это свойство данных.
7. **Ворота для negative** (требование координатора 7; B2, вход 4, п.5): негативный вердикт допускается, только если dry-run на фактическом n показывает долю ложных negative ≤ 0.10 при сильном сигнале (b = 0.8). По v2 (15–16% на n = 12; 0.5–4% на n = 24) на n = 12 negative **недопустим**; допустим при n ≥ 24 историй и формулировке «сильный сигнал (≈ 30% дисперсии y) исключён с ~90% уверенностью».
